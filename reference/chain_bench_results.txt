Both sides were rerun on Alek's Mac in one session (2026-10-23, about 21:10 UTC) after the Merton
fit fix (5786dd0), with the corrected fit: 7,750 strike-row nodes and 30.6M kernel taps.

The first run (Stage 3, commit e92a25b, with the fit from before the fix: 8,391 nodes, 38.0M taps)
gave, as medians: QuantLib Black-Scholes 12.9 ms (1 thread) and 2.4 ms (14 cores), Merton 259.5 ms
and 61.5 ms; GPU Black-Scholes 0.35 ms compute and 39.3 ms end to end, Merton 1.60 ms and 61.3 ms.
Black-Scholes does exactly the same work in both runs, yet it came out about 30% faster in the
second on both QuantLib (12.9 -> 8.8 ms) and the GPU end to end (39.3 -> 27.6 ms): the machine was
in a faster state (power or thermal), not the code. So compare the two sides within one run, as
the table does, and read run-to-run changes of up to ~30% as noise.

Notes. Browser timers here tick in 0.1 ms steps, so the Black-Scholes compute time (0.40 ms) is
only good to about 25%, and so is its ratio to QuantLib. "Compute only" waits on
device.queue.onSubmittedWorkDone, whose wake-up adds jitter: here compute plus read back came out
faster than compute only for both models. End to end is dominated by building kernels and rows in
JavaScript on one CPU thread (25-30 ms per model); the GPU's own share (upload, run, read back) is
1.4-3.2 ms.
